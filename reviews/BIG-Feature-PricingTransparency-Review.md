## Payment runtime, clients, RPCs, and Stripe adapters — reviewed 2026-07-30

- [x] **BUG2 (runtime half) — HIGH — correctness (atomicity/race)** — `api/Concertable.Payment/src/Concertable.Payment.Infrastructure/ManagerPaymentService.cs:2363` and `.../EscrowService.cs:1101` — fixed 2026-07-31 (e2d3fa49)
  Settlement (`PayCommissionAuthorizedAsync`) checks only `transactionRepository.GetSettlementByCommissionAuthorizationIdAsync`, while escrow (`DepositCommissionAuthorizedAsync`/`CaptureCommissionAuthorizedAsync`) checks only `escrowRepository.GetByCommissionAuthorizationIdAsync`; both then call `CalculateAuthorizedAsync` with a null intent, which is fail-open on first use (`IntentMatches` returns true when `bound is null`). Two concurrent calls on one `commissionAuthorizationId` therefore both pass and reach Stripe with distinct idempotency operations (`hold` vs `charge`) → two real charges for one authorization. Fix is BUG2's: persist one shared consumption/claim keyed by authorization id and have both paths atomically claim it (with a DB uniqueness/concurrency guard) before Stripe.

- [x] **BUG3 — HIGH — correctness (race / over-refund)** — `api/Concertable.Payment/src/Concertable.Payment.Infrastructure/EscrowService.cs:1397` — fixed 2026-07-31 (d571836c token + 1dee0bb0 two-phase reserve-then-charge) (`RefundCommissionAuthorizedByBookingIdAsync`; same shape in `RefundAsync:1300`)
  Cumulative-refund enforcement is a read-check-write: it sums `escrow.Refunds`, checks `cumulativeGrossRefund > escrow.PayeeGrossMinor`, then calls Stripe and inserts a new `PaymentRefundEntity`. There is no serialization, no optimistic-concurrency token (grep confirms none exist in `Concertable.Payment`), and the Stripe idempotency key varies by amount (`refund:{CumulativeGrossRefundMinor}`). Two concurrent partial refunds of *different* amounts both load the same prior-refund set, both pass the limit check, and both refund at Stripe under different keys → total refunded exceeds `PayeeGrossMinor`. Fix: add a concurrency token (rowversion) on the escrow / a unique claim per refund and re-check under it, so the second writer fails and retries against the updated total.

- [x] **BUG1 (runtime half) — HIGH — correctness** — `api/Concertable.Payment/src/Concertable.Payment.Infrastructure/EscrowService.cs:1502` — fixed 2026-07-31 (`ExecuteRefundAsync` → `PaymentRefundEntity.CreateCompleted(escrow.Id, …)`)
  All durable refund rows are created only for escrows: `ExecuteRefundAsync` calls `PaymentRefundEntity.CreateCompleted(escrow.Id, …)` and `ManagerPaymentService` has no refund path at all. A direct-settlement (`SettlementTransactionEntity`) refund thus cannot record the immutable per-Stripe-refund facts. Fix is BUG1's: give refund ownership a one-of {settlement, escrow} shape and have the (to-be-added) settlement refund path create and use the durable row.

- [x] **BUG4 — MEDIUM — correctness (idempotency asymmetry)** — `api/Concertable.Payment/src/Concertable.Payment.Infrastructure/ManagerPaymentService.cs:2434` (`CreateCommissionAuthorizedHoldSessionAsync`) — fixed 2026-07-31 (e003eb50)
  Unlike the deposit/capture/pay paths (which short-circuit on an existing row), the hold-session path has no idempotent re-entry and additionally fails closed on a retry: the first call binds the PaymentIntent (`BindPaymentIntent`) and persists it, so a retry (which supplies a null intent) hits `CalculateAuthorizedAsync` with `bound != null && supplied == null` → `commission_authorization_intent_mismatch`, leaving the caller unable to re-obtain the checkout `ClientSecret`. In a PR whose whole point is retry-safe Stripe calls this is a real gap. Fix: make the hold-session path idempotent on retry — detect the already-bound hold intent for this authorization and return the existing session instead of failing the intent check.
